# Plank Differential Fuzzing

## Project Summary

Build a Rust-native differential fuzzing system for `plankc` that adopts the core strategy used by `argotorg/solidity-fuzzing`: generate or mutate programs, compile the same semantic input through multiple compiler configurations, execute the resulting bytecode in an EVM, and report any behavioral mismatch.

The implementation should use idiomatic Rust fuzzing tooling rather than porting the C++/CMake/libFuzzer harnesses from `solidity-fuzzing`. The recommended stack is `cargo-fuzz` for coverage-guided fuzzing, `arbitrary` for structured inputs, and `revm` for deterministic EVM execution.

The goal is to find silent compiler, optimizer, and backend bugs in Plank by comparing independently compiled outputs under the same execution environment.

## Motivation

The current `plankc` test suite already has strong Rust unit/golden tests and Foundry differential tests. The Foundry tests compare fixed Plank programs against Solidity references and fuzz calldata for those programs. That is valuable, but it does not fuzz the compiler input itself.

This project extends coverage from "fixed program, fuzz calldata" to "fuzz program and calldata, then compare compiler outputs." This is the same high-level strategy that makes Solidity's fuzzing infrastructure effective for finding optimizer and code generation bugs.

## Core Strategy

For each fuzz input:

1. Decode a bounded structured input using `arbitrary`.
2. Render it into a Plank program, a SIR program, or both.
3. Compile it through multiple `plankc` configurations.
4. Deploy and call each generated bytecode artifact in the same `revm` environment.
5. Compare observable behavior:
   - success vs revert status
   - return data
   - revert data
   - emitted logs and topics
   - storage and transient storage, once the oracle is mature
6. Treat mismatches as fuzzing findings.
7. Treat invalid programs, expected diagnostics, out-of-gas cases, and known semantic non-equivalences as skips.

The important idea from `solidity-fuzzing` is the differential oracle, not the implementation. Direct code reuse is not recommended because that repository is GPL-3.0, C++-based, and tightly coupled to Solidity internals.

## Recommended Tooling

- `cargo-fuzz`: primary coverage-guided fuzzing driver.
- `arbitrary`: structured input decoding for Plank and SIR program models.
- `revm`: in-process EVM execution and state inspection.
- `proptest`: optional for deterministic property tests and reduced regression cases.
- Normal Rust `#[test]`: replay minimized fuzz cases in CI.

Although `cargo-fuzz` uses libFuzzer underneath, it is the idiomatic Rust interface. The project should avoid a bespoke C++ libFuzzer harness or CMake integration.

## Initial Fuzz Targets

### 1. `plank_backend_diff`

Fuzz generated Plank source programs and compare Plank compiler backends.

Compiler variants:

- `sir-debug`
- `sir-release`
- `sir-release` with optimization sequence `csud`
- `sona` at `O0`
- later: `sona` at `O1`, `Os`, and `O2`

This target exercises:

- parser and source loading
- HIR lowering
- comptime evaluation and type handling
- MIR generation
- SIR lowering and optimizations
- debug backend
- release backend
- Sona backend

The harness should compile in-process through `plank-driver` rather than shelling out to the `plank` binary.

### 2. `sir_backend_diff`

Fuzz SIR programs directly and compare SIR backends and pass configurations.

Compiler variants:

- debug backend without optimization
- release backend without optimization
- release backend with one optimization pass
- release backend with selected pass sequences
- release backend with the standard `csud` sequence

This should be the highest-yield early target because it bypasses Plank source validity issues and focuses on optimizer/codegen behavior.

The target should mirror Solidity's Yul fuzzing approach: compare "before optimization" vs "after optimization", and add single-pass differential targets to isolate pass-specific bugs.

## Fuzz Input Design

Start with structured, bounded inputs rather than raw bytes interpreted as source.

Example logical input shape:

```text
FuzzCase {
  program_model,
  calldata,
  call_value,
  environment,
  backend_subset,
}
```

For Plank source generation, begin with a small expression and statement language:

- `u256` literals
- `bool` literals
- arithmetic and bitwise operations
- comparisons
- `if` expressions
- bounded `while` loops or no loops initially
- memory load/store
- calldata load/copy
- return/revert/stop
- simple constants and local variables

Avoid advanced language features until the oracle is stable:

- external calls
- contract creation
- bytecode introspection
- gas-sensitive programs
- unbounded loops
- large memory expansion

For SIR generation, prefer constructing legal `EthIRProgram` values directly where possible. If text rendering is easier initially, generate SIR text and parse it, but the long-term target should be structured IR generation so invalid syntax does not dominate the corpus.

## Differential Oracle

The oracle should compare only semantic observations that are expected to be stable across compiler variants.

Initial comparison:

- top-level status: success vs revert
- return data for successful calls
- revert data for reverting calls
- logs: topics and data, ignoring address if backend-dependent deployment addresses are involved

Later comparison:

- persistent storage
- transient storage
- multi-contract state changes

False-positive avoidance should be designed from the start. Inputs should be skipped when:

- compilation produces normal diagnostics
- bytecode generation returns an expected backend error
- deployment fails in a non-comparable way
- execution runs out of gas
- a subcall runs out of gas
- the program explicitly observes gas
- the program observes compiler-dependent bytecode layout

Operations to avoid or classify carefully at first:

- `@evm_gas`
- `@evm_codesize`
- `@evm_codecopy`
- `@evm_extcodesize`
- `@evm_extcodecopy`
- `@evm_extcodehash`
- `@runtime_start_offset`
- `@init_end_offset`
- `@runtime_length`
- `CREATE` and `CREATE2`, until account normalization is implemented

Storage comparison should eventually normalize accounts by creation order rather than concrete address, following the idea used by `solidity-fuzzing`.

## Reproducer Workflow

Every fuzz finding should be easy to replay outside the fuzz engine.

Add a small repro/debug runner that accepts a saved fuzz input and writes:

- generated `.plk` or `.sir`
- calldata
- environment settings
- bytecode per backend/configuration
- execution result per backend/configuration
- a concise diff of the first mismatch

This is essential. Without a repro workflow, fuzzing output is hard to triage and unlikely to be maintained.

Minimized findings should be converted into normal regression tests:

- Rust unit tests for compiler-internal bugs
- SIR pass tests for optimizer bugs
- Foundry diff tests only when the issue is best represented as end-to-end contract behavior

## Relationship To `solidity-fuzzing`

Ideas to adopt:

- compile-run-compare differential oracle
- comparing optimizer configurations
- single-pass optimizer fuzzing
- generated structured inputs instead of mostly raw text
- explicit skip policy for expected non-bugs
- corpus/reproducer workflow
- source plus calldata as one fuzz input
- storage/log comparison discipline

Ideas not to copy directly:

- C++/CMake harness architecture
- evmone-specific host implementation
- Solidity/Yul protobuf generators as Plank generators
- GPL-licensed source code

The useful output of the deep dive is a design pattern, not a dependency.

## Possible AFL/Tree-Sitter Follow-Up

The monorepo already has `plank-tree-sitter`, so an AFL-style source mutator could be useful later:

- seed from existing `.plk` programs in `plank-diff-tests`
- use tree-sitter-aware AST splicing
- preserve calldata as a separate region in the input
- use a CLI repro runner for crashes

This should be a later phase. `cargo-fuzz` with structured `arbitrary` inputs is simpler and should find backend bugs sooner.

## Phased Plan

### Phase 1: Rust Fuzzing Skeleton

- Add `plankc/fuzz` with `cargo-fuzz`.
- Add shared harness utilities for:
  - compiling Plank in-process
  - compiling SIR in-process
  - deploying and calling bytecode in `revm`
  - comparing execution results
- Add a tiny initial corpus from existing Plank/SIR examples.

### Phase 2: SIR Differential Fuzzer

- Implement `sir_backend_diff`.
- Generate simple legal SIR programs.
- Compare debug and release backends.
- Add optimization sequence variants.
- Add single-pass variants to isolate optimizer bugs.

### Phase 3: Plank Backend Differential Fuzzer

- Implement `plank_backend_diff`.
- Generate bounded Plank source snippets.
- Compare `sir-debug`, `sir-release`, optimized SIR release, and Sona.
- Add skip filters for unstable builtins and gas-sensitive behavior.

### Phase 4: Reproducer And Regression Flow

- Add a debug runner for saved fuzz inputs.
- Dump generated source, bytecode, calldata, and execution diffs.
- Add minimized findings as ordinary tests.

### Phase 5: Richer Program Generation

- Add structs, tuples, functions, imports from `std`, ABI helpers, storage helpers, and bounded loops.
- Add storage comparison with account normalization.
- Add multi-call sequences to test persistent state transitions.

### Phase 6: Optional Tree-Sitter/AFL Experiments

- Explore `plank-tree-sitter` with a source-splicing mutator.
- Use existing Plank examples as seed corpus.
- Preserve calldata in a separate input region.

## Success Criteria

The project is successful when:

- fuzz targets run continuously for hours without excessive false positives
- minimized inputs replay deterministically
- backend mismatches produce useful diagnostics
- at least one SIR/backend regression test can be derived from a fuzz finding
- the harness can be run locally by a Plank developer with standard Rust tooling

## Non-Goals

- Do not port `solidity-fuzzing` C++ code.
- Do not make the fuzzing harness depend on Foundry.
- Do not require Docker or OSS-Fuzz infrastructure for local use.
- Do not attempt full Plank-vs-Solidity generated-source equivalence in the first version.
- Do not compare gas usage as a semantic oracle.

## Long-Term Direction

After backend-internal fuzzing is stable, consider a shared mini-contract model with two emitters:

- Plank emitter
- Solidity or Yul reference emitter

That would extend the existing handwritten Plank-vs-Solidity Foundry tests into generated source-level differential testing. It is more ambitious than backend differential fuzzing and should come after the core Rust fuzzing infrastructure is proven.
